# AGENTS.md

C# incremental source generator (published as the NuGet package `Aot.ArgumentParser`). Users annotate a `partial` class with `[ParameterCollection]` and properties with `[Flag]`/`[Option]`/`[Positional]`. The generator adds a reflection-free, AOT-friendly `static Parse(string[] args)` returning `(instance, List<ArgumentParserException>)`. User-facing docs are in `README.md`; release history in `CHANGELOG.md`.

## Code style
- Indent with **tabs** (see `.editorconfig`), LF line endings, one final newline. Run `make format` before committing; CI fails on formatting differences. Use tabs in any code snippet you write, including snippets inside generated-code string templates and markdown.
- Don't add comments to the code that the generator emits unless essential.
- XML doc comments are expected on public members: both library projects build with `AnalysisMode=All`, `GenerateDocumentationFile` and `TreatWarningsAsErrors`, so a new analyzer warning or a missing doc comment fails the build.

## Commands
Everything goes through the `Makefile` (stamp files in `.build-stamps/` skip up-to-date steps; `make clean` resets them).

```bash
make build-analyzer        # dotnet build ArgumentParser -c Release (also builds the Analyzer and packs the nupkg into ArgumentParser/bin/nupkg)
make test                  # builds tests in Debug, then runs them with coverage
make format                # dotnet format (whitespace, line endings, import order); CI runs 'make format-check', which fails on any difference
make smoke-test            # publishes ExampleConsole as a native AOT executable against the locally packed nupkg and runs scripts/smoke-test.sh against it
make all                   # analyzer + example + tests
make help                  # lists every target
```

Run a subset of tests directly (the xunit project targets net10.0, Debug only; never Release, stack traces are wanted):

```bash
dotnet test ArgumentParser.Tests --filter "FullyQualifiedName~HelpTextTests"
dotnet test ArgumentParser.Tests --filter "FullyQualifiedName=ArgumentParser.Tests.BasicSourceTextGeneratorTests.Generator_DeclaresParseMethod"
```

Gotchas with the Makefile:
- `make build-example` / `restore-example` deliberately consumes the example as a real NuGet consumer, to prove the packed nupkg (analyzer DLL under `analyzers/dotnet/cs/`) works end to end. Every local build reuses the same version, so the global NuGet cache (`~/.nuget/packages/aot.argumentparser/<version>`) can serve a stale copy instead of the fresh nupkg; the recipe no longer clears it (`dotnet nuget locals all --clear` wiped the whole cache), so delete that one folder by hand when the example must pick up generator changes. `dotnet add ... --source ArgumentParser/bin/nupkg --prerelease` is pinned with `--version` taken from `ArgumentParser/ArgumentParser.csproj`, because the (gitignored) nupkg folder accumulates old packages and without the pin the highest one wins (it used to rewrite `ExampleConsole/ExampleConsole.csproj` to e.g. 1.4.0 instead of 1.3.0). Bumping `<Version>` therefore also needs the `PackageReference` in `ExampleConsole.csproj` updated, which `make restore-example` does.
- `build-example` runs `dotnet publish -c Release`, so the smoke test exercises the real NativeAOT binary (needs clang and zlib; `TreatWarningsAsErrors` makes trim/AOT warnings fail the build). A plain `dotnet build` only gives a JIT-run apphost plus a managed dll, and `smoke-test.sh` refuses such a binary. `ExampleConsole` pins `RuntimeIdentifier` to `linux-x64` (AOT ILCompiler package workaround), so the binary is at `ExampleConsole/bin/Release/net10.0/linux-x64/publish/ExampleConsole`, which is what `smoke-test` runs.

## Architecture
Three projects matter; keep the split in mind because it is not obvious from the names:

- **`ArgumentParser/`** (assembly `Aot.ArgumentParser`, multi-targets netstandard2.0 to net10.0): the *runtime* library the user's program references. Contains the attributes (`Attributes.cs`), config enums, `ArgumentTokenizer`, `Token` types, and the `ArgumentParserException` hierarchy. Generated code calls into this (`global::ArgumentParser.ArgumentTokenizer`, `OptionToken`, ...). It is also the NuGet packaging project: it embeds the Analyzer DLL from `ArgumentParser.Analyzer/bin/Release/netstandard2.0/` under `analyzers/dotnet/cs/`, so the Analyzer must be built in **Release** before packing (the netstandard2.0 `ProjectReference` with `ReferenceOutputAssembly=false` enforces build order). `ArgumentParser/Internal/*.cs` are empty, tracked leftovers; the real code lives in the Analyzer project.
- **`ArgumentParser.Analyzer/`** (netstandard2.0, Roslyn 4.12): the generator itself. Pipeline in `ParserGenerator.cs`, split in two so it stays incremental:
  1. `ForAttributeWithMetadataName("ArgumentParser.ParameterCollectionAttribute")` finds classes. Its transform (`ExtractModel`) is the only place that reads syntax, symbols or the semantic model, and it returns a `ClassModel` (`Utilities/ClassModel.cs`): plain data with value equality (strings, bools, `EquatableArray`, `DiagnosticInfo`). Roslyn compares models and skips the output step when the model is equal. Never put a symbol, syntax node, `Location` or `Compilation` in the model.
  2. Inside `ExtractModel`: `Validation.ValidateClassDeclaration` (ARG001/002/006), then `GeneratorConfiguration` (`Utilities/Configuration.cs`) reads the `[ParameterCollection]` constructor args, `AttributeFactory` (`Utilities/`) turns property attributes into `PropertyAndAttributeInfo`, `ArgumentProvider` groups them, and `Validation.ValidateAttributes` / `ValidateGenerationOptions` check them. Each stage returns early with a model that only carries the diagnostics. Validation produces `DiagnosticInfo` (descriptor, args and a `LocationInfo` file/span) instead of `Diagnostic`.
  3. The output step (`GenerateSource`) reports the diagnostics (`DiagnosticInfo.ToDiagnostic`), stops if the model has errors (ARG008 is the only warning), and otherwise rebuilds `ArgumentProvider`/`HelptextProvider` from the model and runs `SourceTextGenerator`, which emits `<Namespace>.<ClassName>_Parser.g.cs` as a string with `AssemblyVersionProvider.FullSemVer` stamped into `[GeneratedCode]`.
  The tree of commands (`[CommandApp]`, `[Command]`) has its own pipeline next to this one, all in `ParserGenerator.Initialize`. Two providers (`RootModels`, `CommandModels`) run `CommandNodeExtractor.Extract`, the only place that reads symbols for the tree, and return a `CommandNodeModel`: a location-free `CommandNodeInfo` (kind, name, description, annotations, child property candidates), the options and flags of the node (`NodeArguments`; a leaf's are only there so names can be compared along the tree, its parser and argument rules stay with the `ClassModel`), and the locations and node-level diagnostics (ARG014 to ARG016 and ARG023 to ARG025, plus the attribute rules for the options of a group, ARG026 included). `NodeSources` (the same without locations) are collected and linked by `CommandTreeLinker.Link` (`LinkedTrees`) into one `CommandTree` per root, plus `LinkProblem`s (each carrying its `DiagnosticDescriptor`) for the rules that need the whole tree (ARG017 to ARG022, and ARG027 for an option or flag name that a command above uses), which are turned into diagnostics with `ToDiagnostics` using the locations of the models (`ChildLocations`, `ArgumentLocations`). An argument attribute on a property of a command class type is ARG026 (checked in `Validation.ValidateCommandClassArguments` for every class); the linker does not treat it as a child and keeps ARG019/ARG020 quiet about it. Trees without errors are generated by `CommandTreeSourceGenerator` into `<Namespace>.<ClassName>_Command.g.cs` for the root and every group (leaves only have their own `_Parser.g.cs`): an internal `ParseCore` that reads the options of the level with `ArgumentTokenizer.TokenizeLeadingArguments` and calls `ParseCore` of the child it names, and for the root also a public `Parse` and the `Commands` list. Classes nested in other types are supported: the models carry `ContainingType`s (keyword and name, outermost first) and `SourceTextGenerator.WriteClassStart/End` declare the surrounding types as partial again; file names are built with `ContainingType.QualifiedName` (names only, never `ToDisplayString()`, which holds `<T>`, and without the `@` of a keyword name, which `AddSource` rejects; names in code keep it, see `ContainingType.EscapeIdentifier`). The generated part of a class has no access modifier, so it takes the user's (`internal partial` must work). The arguments of every class, leaf, group or root, are read from every part of a partial class (`DeclarationParts`, ordered by file path), and the class-level checks look at the members of every part; child properties are only what the class declares itself (inheritance is unsupported, see ARG020). A root that also has `[ParameterCollection]` (ARG016) leaves its class and argument rules to the leaf pipeline, so they are not reported twice. Attribute names and argument reading for both pipelines are in `Utilities/AttributeReader`. The pieces shared with the leaf generator (`WriteTokenLoop` and friends) are `internal static` in `SourceTextGenerator`. Keep locations out of everything that reaches `LinkedTrees`, or an edit that only moves code relinks and regenerates the tree; the `NodeSources` and `LinkedTrees` step names let `IncrementalityTests` check that.
  Because diagnostic locations are file/span data, `#pragma` and `.editorconfig` cannot suppress them (only `NoWarn` can). When you add a field the generator needs, add it to the model and to its `Equals`/`GetHashCode`, or edits to it will not regenerate; `IncrementalityTests` guards both directions.
  The generator must stay netstandard2.0 and satisfy `EnforceExtendedAnalyzerRules`. The generated file starts with its own `using System; System.Collections.Generic; System.Linq;` so it compiles in projects without `ImplicitUsings`. Names and descriptions go into the generated code through `Literal(...)` (Roslyn `SymbolDisplay.FormatLiteral`), and the help text raw string picks a delimiter longer than any quote run in its content; keep using those instead of interpolating raw strings into generated code. Refer to library types as `global::ArgumentParser.X` in generated code: a user namespace such as `MyApp.ArgumentParser` would otherwise capture `ArgumentParser.X`. Per-call state such as `requiredProperties` must be a local of `Parse`, never static.
- **`ArgumentParser.Tests/`** (xunit, net10.0): `Helpers/TestHelper.GetGeneratedOutput(source)` compiles a source string and runs `ParserGenerator` through `CSharpGeneratorDriver`, returning diagnostics plus the first generated file. `Helpers/SourceCodeBuilder` assembles test class source from `PropertyAndAttributeInfo`s. Tests assert on substrings of generated text, so changing emitted code formatting can break many tests. `ArgumentTokenizerTests` tests the runtime tokenizer directly. `RuntimeLibraryTests` covers the attributes, exceptions and tokens; `AttributeExtractionTests` drives `AttributeFactory`, `GeneratorConfiguration` and the pipeline components directly from a `TestHelper.CreateCompilation` compilation; `DiagnosticRuleTests` covers every ARG rule. `CommandNodeExtractionTests`, `CommandTreeLinkerTests` and `GeneratedCommandTreeTests` cover the tree of commands (reading nodes, linking and its rules, and compiling and running a generated tree). `IncrementalityTests` tracks the driver's pipeline steps to check that unrelated edits reuse the cached output and that edits to the annotated class regenerate it. `ClassModelTests` covers the comparable model types. `GeneratedParserBehaviourTests` (via `Helpers/GeneratedParser` and `ParserSource`) compiles the generated parser with a test class, loads it, calls `Parse` and asserts on results; prefer it for behaviour changes. Use `ThrowNever`/`ThrowIfAnyError` plus `GenerateTextOnly`/`GenerateArgumentOnly` there, because `GenerateAll` or the default `DisplayHelpAndExit` call `Environment.Exit` and would kill the test host. If you find a generator bug, add a failing test here first (a `Skip` with the reason is fine until it is fixed).
- `ExampleConsole/` is the demo/smoke-test app (`PublishAot`, consumes the locally built nupkg). `Program.cs` takes a scenario as its first argument (`lenient`, `strict`, `required`, otherwise the default `MyCommandLineArguments`) so every `BehaviourOnError` mode and every supported property type can be reached; the scenario classes live in `ScenarioArguments.cs`. `scripts/smoke-test.sh` runs the binary with ~50 command lines and checks exit code and output lines; add a `check ...` call there when adding behaviour to the example.
- `ArgumentParser.CodeFixes/` is gitignored build leftovers; code fixes are unimplemented (see `TODO`).

### Where changes usually land
- **New or changed diagnostic (ARGnnn)**: add the descriptor in `GeneratorDiagnostics.cs`, the check in `Validation.cs` (or in `CommandTreeLinker` for a rule that needs the whole tree), a rule entry in `ArgumentParser.Analyzer/AnalyzerReleases.UnShipped.md` (note the capital S), a doc page `ArgumentParser.Analyzer/docs/rules/ARGnnn.md`, and a case in `DiagnosticRuleTests.cs` (or `CommandTreeLinkerTests.cs`). `DiagnosticRuleTests` checks that descriptors are numbered without gaps and that every one has its doc page and release row.
- **New attribute option or supported type**: touch `ArgumentParser/Attributes.cs` (runtime), `Utilities/AttributeFactory.cs` (extraction), `Validation.cs`, `SourceTextGenerator.cs` (emission), and the README type list. The tokenizer only changes if token semantics change.
- **Tokenizer behaviour** (flag repeat counts, short-name clusters like `-llvt`) lives only in the runtime `ArgumentTokenizer`; the generated `Parse` consumes the resulting tokens.

## Versioning and releases
- Version bumps come from GitVersion (`GitVersion.yml`): commit-message tags `+semver: fix|minor|major` or branch names `fix/`, `feature/`, `breaking/`.
- The version string exists in `ArgumentParser.Analyzer/CodeProviders/AssemblyVersionProvider.cs`, `ArgumentParser/ArgumentParser.csproj` (`<Version>`), and `ExampleConsole.csproj`; `make set-version-stable` / `set-pre-release-version` rewrite the first two with `sed` and **`git commit --amend`** the latest commit. Don't run those targets casually. Releases are cut locally (`make pre-release` / `make release-stable`); no CI workflow does it.
- Add user-visible changes to `CHANGELOG.md` under "UnReleased".
